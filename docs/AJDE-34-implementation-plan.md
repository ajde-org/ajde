# AJDE-34: AI rate limiting implementation plan

Prevent AI spam without making normal users manage a visible quota. Implement on `feat/AJDE-34-ai-rate-limiting`, branched from `dev`. Scope is AI entry points only; general endpoint protection and per-user token budgets are deferred.

Work through the four sections in order. Each is a session-sized workstream, not a requirement to finish in one session. Check tasks only when implemented and verified. Before each session, read the repository instructions and inspect the current diff; before stopping, update the handoff at the end with completed work, checks, and the next task. All paths below are relative to the repository root.

## 1. Policy and atomic database admission

The revised starting policy is:

| Control | Per-user limit |
| --- | --- |
| Explicit AI actions, shared across features | 30 per rolling hour |
| Screenshot reads, also consuming the shared allowance | 10 per rolling hour |
| Burst allowance shared across explicit actions | Bucket capacity 4; refill 1 permit every 10 seconds |
| Concurrent explicit operations | 2 |
| Automatic explanation requests, separate allowance | Proposed: 60 per rolling hour and 2 concurrent |

The explanation allowance is an implementation starting proposal, not a measured usage requirement. It must be configurable and must never consume explicit-action permits. Each explanation request is already a bounded batch of rides. On denial, omit optional explanations while retaining complete ride cards.

One explicit action includes all its internal model calls, checker rounds, and location fallbacks. Screenshot reading and subsequent text import remain separate actions in the current UI. Request permits are unrelated to model input/output tokens.

- [x] Define typed feature names and one server-owned policy configuration. Never accept thresholds or policy-group selection from the browser. Keep the limits above configurable, with documented defaults and valid ranges.
- [x] Read `ride-share-app/supabase/DATABASE_MODELS.md` and the existing `chat_ai_budgets` / `try_chat_ai_request()` implementation. Design a replacement supporting shared allowances, screenshot admissions, burst state, and expiring operation leases.
- [x] Store indexed admission timestamps per user and policy group. Count admissions strictly newer than database time minus one hour; expire them individually rather than resetting on clock-hour boundaries. Retain screenshot identity for its additional sublimit.
- [x] Implement a single atomic admission RPC. Derive the caller from the authenticated session and serialize competing admissions for that user, including the first-ever admission when no budget row exists. Check the rolling window, screenshot sublimit when applicable, token bucket, and active leases together. On success, record admission, consume one burst permit, and create a unique lease in the same transaction. On denial, consume no additional allowance.
- [x] Calculate burst refill from elapsed database time, cap available permits at 4, and preserve partial refill progress. Avoid scheduled refill jobs. Compute the next eligible time for every exhausted constraint and return the longest applicable wait.
- [x] Add idempotent lease release and lease expiry. Set an overall operation deadline shorter than its lease lifetime, including bounded model rounds and retries. Do not expire a lease while its operation can still legally start paid work. Return a conservative retry time for concurrency denials.
- [x] Return a typed admission result: admitted operation ID or denial reason, `retryAfterSeconds`, and retry time. Distinguish limiter storage failure from quota denial; storage failure prevents paid work and becomes a retryable service error.
- [x] Define the counting boundary as successful admission immediately before paid work. Invalid/unauthorized requests and missing configuration detected beforehand consume nothing. Once admitted, keep the count on provider failure, refusal, timeout, or cancellation; release concurrency separately. Avoid refunds that create a retry bypass.
- [x] Create migration files through the repository workflow. Enable RLS, revoke direct client table access, restrict function execution, and use fixed search paths and authenticated identity checks for any necessary privileged functions. Ensure clients cannot release another operation or manufacture capacity. Define retention and cleanup for expired admissions/leases.
- [x] Update `DATABASE_MODELS.md`, regenerate `ride-share-app/lib/supabase/database.types.ts`, and extend privilege/RLS tests. Test local migrations only; do not apply an unmerged migration to production.

## 3. Usage accounting and recovery experience

Rate limits protect request frequency. Token usage measures cost separately; do not turn short versus long user text into a visible credit system.

- [x] Add common usage capture for every provider call, both SDK and direct HTTP. Record operation ID, feature, user ID, actual model, input tokens, cached input tokens, output tokens, duration, and outcome. Sum all rounds under the originating operation; keep any reported reasoning breakdown informational rather than double-counting output tokens.
- [x] Calculate estimated cost using a versioned model-price configuration that distinguishes cached input from uncached input and output. Unknown models or missing usage remain explicitly unknown, never zero. Include costs from successful provider responses even when parsing or later pipeline steps fail. Timeouts/cancellations may have unknown billable usage.
- [x] Keep prompts, images, chat transcripts, and generated responses out of accounting records. Store only the minimum metadata needed for diagnosis and aggregate reporting. Add retention/cleanup, restricted access, migrations, generated types, and database tests for any new persisted records. Accounting failures must be observable and must not trigger a second model execution.
- [x] Preserve entered text/uploads on rate-limit errors. Disable duplicate submission while pending, display the server-provided retry time only after denial, and permit a deliberate retry when eligible. Do not show a remaining-quota counter or add automatic retry loops.
- [x] Keep manual search, ride entry, and ordinary chat available when AI is limited. A blocked automatic explanation should quietly leave the complete ride cards visible. Ensure automatic explanation effects do not repeatedly request the same pending work.
- [x] Add typed English/Macedonian messages through the existing i18n workflow. Check keyboard behavior and the blocked/retry states at approximately 375px and desktop widths. Record required human review of Macedonian messages before a PR.
- [x] Test usage aggregation across multiple rounds, cached-token pricing, unknown usage, provider failure, accounting failure, and duplicated operation IDs. Verify retry messages and manual fallbacks without live AI requests.

Completion: normal users see no quota-management UI, blocked users can recover without losing work, and operators can distinguish expensive features from high request counts.
